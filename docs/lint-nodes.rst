Lint Rule Node Reference
========================

The syntax-tree classes a declarative lint rule reads, generated from the
lint engine's reflection tables and ``ast/*.yaml`` by
``scripts/gen_lint_nodes.py`` -- do not edit this file by hand, it will be
overwritten.

A class name is a node kind: ``match: { kind: Field }`` matches it,
``n.isa(Field)`` and ``type(n) == Field`` test for it, and a subclass
matches wherever its base does. A rule reads a node's fields by name,
``node.name.id``, including the fields its bases declare: a ``Field`` has
``name`` from ``NamedScopeChild`` and ``location`` from ``ScopeChild``. An
unset node field is ``null``, an unset list is empty; test with ``has()`` or
read it with ``.?`` (see :doc:`lint-rule-authoring`). The functions that
move around the tree and read the linked model are in :doc:`lint-functions`.

The types are as the rule checker gives them. An enum field is an ``int``
compared against its constants (``node.op == ExprBinOp.BinOp_Eq``); a flags
field is a set of flags, tested with ``has_flag`` (see `Enums`_). Fields of
the linker's own classes that a rule cannot read are left out.

.. _lint-node-Action:

``Action``
~~~~~~~~~~

Base: :ref:`TypeScope <lint-node-TypeScope>`.

Action declaration defining reusable behavior blocks.

Actions are the fundamental unit of behavior in PSS. They encapsulate data (fields), constraints, and activities (control flow). Actions can be composed hierarchically and randomized according to constraints.

.. code-block:: none

   action my_action {
       rand int addr;

       constraint {
           addr >= 0x1000;
           addr < 0x2000;
       }

       activity {
           do_read(addr);
       }
   }

.. _lint-node-AssocData:

``AssocData``
~~~~~~~~~~~~~

Base class for user-defined associated data attached to AST nodes.

Allows users to attach custom metadata to any AST node without modifying the core AST structure. Used for annotations, analysis results, or custom transformations.

.. _lint-node-Comment:

``Comment``
~~~~~~~~~~~

Base: :ref:`ScopeChild <lint-node-ScopeChild>`.

A source comment captured verbatim and in normalized form.

Collected only when the builder has ``setCollectComments(true)``. Leading and trailing comments hang off the ``comments`` list of the ``ScopeChild`` they document; orphans -- comments a blank line has detached from any construct -- collect in the enclosing ``Scope.trailing_comments``.

.. list-table::
   :header-rows: 1
   :widths: 20 25 55

   * - Field
     - Type
     - Description
   * - ``text``
     - ``string``
     - normalized content, comment markers and the ``*`` gutter removed
   * - ``placement``
     - ``CommentPlacement`` enum (see :ref:`lint-enum-CommentPlacement`)
     - how the comment relates to its owner
   * - ``raw``
     - ``string``
     - the untouched source text, delimiters included
   * - ``is_block``
     - ``bool``
     - true for ``/* */``, false for ``//``

.. _lint-node-CompileCond:

``CompileCond``
~~~~~~~~~~~~~~~

A ``compile if`` or ``compile assert``, kept after the builder has evaluated it (pss-scrambler FR-002 case A).

The builder still decides which branch to elaborate, from the parse tree, exactly as before; this record only keeps what that decision dropped: the condition, with its references, and where each branch that was not elaborated is in the source.

The linker resolves the condition's references in the enclosing scope without reporting anything -- ``compile has(X)`` names things that may legitimately not exist.

.. list-table::
   :header-rows: 1
   :widths: 20 25 55

   * - Field
     - Type
     - Description
   * - ``kind``
     - ``CompileCondKind`` enum (see :ref:`lint-enum-CompileCondKind`)
     - if or assert
   * - ``cond``
     - :ref:`Expr <lint-node-Expr>`
     - The condition, as an ordinary expression
   * - ``taken``
     - ``int``
     - Index of the elaborated branch (0: the ``if`` branch, 1: the ``else`` branch), or -1 if neither was (the condition was false with no ``else``, or could not be evaluated)
   * - ``eval_failed``
     - ``bool``
     - The condition could not be evaluated
   * - ``inactive``
     - ``list(SourceRange)``
     - The branches not elaborated, in source order
   * - ``location``
     - ``Location``
     - Where the statement starts
   * - ``msg``
     - ``string``
     - An assert's message, unquoted; empty if none
   * - ``deferred``
     - ``bool``
     - An assert on a template parameter, in a generic type's body. The builder leaves it alone; each specialization evaluates its own copy after linking (symbol-resolution plan 8.5)

.. _lint-node-ComponentBind:

``ComponentBind``
~~~~~~~~~~~~~~~~~

Base: :ref:`ScopeChild <lint-node-ScopeChild>`.

Component-level object/pool bind directive (``bind pool targets;``).

Binds a pool to a set of action object-reference fields, or to all compatible references via the wildcard form. Every target -- including a wildcard -- is a ``ComponentBindTarget``, so a mixed list such as ``bind p { a.x, * }`` keeps both entries in source order.

The pool is an ordinary reference from the binding component. A target's path elements, action type and field are resolved along the component path (LRM 12.3): each element in the component the previous one reaches, the action type in the last component reached, the field in that action type.

.. code-block:: none

   component pss_top {
       pool my_buffer p;
       bind p *;                       // wildcard
       bind p { producer.out };        // explicit target path
       bind p { sub[0..3].prod.out };  // indexed component path
   }

.. list-table::
   :header-rows: 1
   :widths: 20 25 55

   * - Field
     - Type
     - Description
   * - ``pool_path``
     - :ref:`ExprRefPathContext <lint-node-ExprRefPathContext>`
     - Path to the bound pool (e.g. ``p``, ``gfx0.pool``).
   * - ``is_wildcard``
     - ``bool``
     - True if \*any\* target is a wildcard -- for the bare ``bind p *;`` form, and for a mixed list containing ``*``. Equivalent to ``any(t.is_wildcard for t in targets)``, and retained as a shorthand for the overwhelmingly common bare form.
   * - ``targets``
     - list of :ref:`ComponentBindTarget <lint-node-ComponentBindTarget>`
     - The bind targets in source order, one ``ComponentBindTarget`` per entry.

.. _lint-node-ComponentBindTarget:

``ComponentBindTarget``
~~~~~~~~~~~~~~~~~~~~~~~

Base: :ref:`ScopeChild <lint-node-ScopeChild>`.

One entry in a ``bind`` directive's target list.

Corresponds to ``object_bind_item_path`` in the grammar: a possibly empty component-instance path followed by the bind item itself, which is either ``*`` or ``ActionType.field`` with an optional index selection.

A wildcard entry sets ``is_wildcard`` and leaves ``type_id``, ``field`` and ``range`` null. Because the wildcard is a target like any other, a mixed list keeps its shape: ``bind p { a.x, * }`` has two targets rather than one target plus a flag.

.. code-block:: none

   component pss_top {
       pool my_buffer p;
       bind p { sub[0..3].prod.out };
       //       path -----^     ^--- type_id="prod", field="out"
       bind p { a.x, * };  // two targets, the second a wildcard
   }

.. list-table::
   :header-rows: 1
   :widths: 20 25 55

   * - Field
     - Type
     - Description
   * - ``is_wildcard``
     - ``bool``
     - True for the ``*`` form.
   * - ``path``
     - list of :ref:`ComponentPathElem <lint-node-ComponentPathElem>`
     - Leading component-instance path elements (empty when the target names an action in the enclosing component).
   * - ``type_id``
     - :ref:`TypeIdentifier <lint-node-TypeIdentifier>`
     - Action type of the bind item; null when wildcard.
   * - ``field``
     - :ref:`ExprRefName <lint-node-ExprRefName>`
     - Object-reference field on that action; null when wildcard.
   * - ``range``
     - :ref:`ExprDomainOpenRangeList <lint-node-ExprDomainOpenRangeList>`
     - Optional index / index-range selection on the field; null when absent or wildcard.

.. _lint-node-ComponentPathElem:

``ComponentPathElem``
~~~~~~~~~~~~~~~~~~~~~

Base: :ref:`ScopeChild <lint-node-ScopeChild>`.

One component-instance step of a ``bind`` target path.

Corresponds to ``component_path_elem`` in the grammar: a component instance name with an optional index or index-range selection. The index selection is the reason this class exists -- it was previously folded into the target's dotted text, where a consumer could neither read the indices nor tell them from part of a name.

.. code-block:: none

   component pss_top {
       pool my_buffer p;
       bind p { sub[0..3].prod.out };
       //       ^^^^^^^^^ one ComponentPathElem, id="sub",
       //                 range=[0..3]
       //                 ^^^^ a second, id="prod", no index
   }

   :header-rows: 1
   :widths: 20 25 55

   * - Field
     - Type
     - Description
   * - ``id``
     - :ref:`ExprRefName <lint-node-ExprRefName>`
     - The component instance name.
   * - ``range``
     - :ref:`ExprDomainOpenRangeList <lint-node-ExprDomainOpenRangeList>`

.. _lint-node-TemplateElem:

``TemplateElem``
~~~~~~~~~~~~~~~~

Base: :ref:`SymbolScope <lint-node-SymbolScope>`. Subclasses: :ref:`TemplateAssign <lint-node-TemplateAssign>`, :ref:`TemplateBlock <lint-node-TemplateBlock>`, :ref:`TemplateComment <lint-node-TemplateComment>`, :ref:`TemplateExpr <lint-node-TemplateExpr>`, :ref:`TemplateIf <lint-node-TemplateIf>`, :ref:`TemplateText <lint-node-TemplateText>`, :ref:`TemplateVarDecl <lint-node-TemplateVarDecl>`.

Base class for one element of a scanned template string.

Every element records where it came from in the owning TemplateString's ``raw`` text.  A ``Location`` is not enough for a renderer that wants to splice, so byte offsets are carried as well.

Note this derives from SymbolScope rather than plain ScopeChild. Only the block elements actually need a symbol table, but the name resolution machinery requires a scope pushed onto the resolution stack to be an ISymbolScope -- ``AstSymbolTableIterator:: getSymScopeBack()`` silently \*erases\* anything else from the stack. Keeping one hierarchy avoids duplicating offset/extent across two parallel ones.  The ``name`` inherited from SymbolChildrenScope is a fixed kind tag (``<template-text>``, ``<template-if>``, ...), which also makes the resolver's debug output readable.

.. list-table::
   :header-rows: 1
   :widths: 20 25 55

   * - Field
     - Type
     - Description
   * - ``offset``
     - ``int``
     - Byte offset into the owning TemplateString's raw text
   * - ``extent``
     - ``int``
     - Length in bytes, including the delimiters
   * - ``is_own_line``
     - ``bool``
     - True when this element's line holds directives and whitespace only.  §4.7.1.2 excludes that whitespace and the terminating newline from the expansion; deciding it needs the raw text, so the scanner computes it once and records it here rather than making every renderer re-scan.

.. _lint-node-TemplateCategoryTypeParamDecl:

``TemplateCategoryTypeParamDecl``
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

Base: :ref:`TemplateParamDecl <lint-node-TemplateParamDecl>`.

Category-constrained type template parameter declaration.

Declares a template type parameter constrained to a specific type category (action, component, buffer, resource, state, stream, or struct). This ensures type safety by restricting template instantiation to compatible types. An optional restriction can further narrow the accepted types to a specific base type or interface, and a default type can be provided.

.. code-block:: none

   // Action category constraint
   component action_container<T: action> {
       T action_inst;

       activity {
           do action_inst;
       }
   }

   // Resource category constraint with default
   action resource_user<R: resource = my_resource_t> {
       lock R resource_lock;
   }

   // Component category constraint
   component comp_wrapper<C: component> {
       C wrapped_comp;
   }

   // Instantiation examples
   action_container<my_action_t> container;
   resource_user<custom_resource_t> user;
   resource_user<> default_user;  // Uses my_resource_t

.. list-table::
   :header-rows: 1
   :widths: 20 25 55

   * - Field
     - Type
     - Description
   * - ``category``
     - ``TypeCategory`` enum (see :ref:`lint-enum-TypeCategory`)
     - Required type category (Action, Component, etc.)
   * - ``restriction``
     - :ref:`TypeIdentifier <lint-node-TypeIdentifier>`
     - Optional base type or interface that must be satisfied
   * - ``dflt``
     - :ref:`DataType <lint-node-DataType>`
     - Optional default type if not specified during instantiation

.. _lint-node-ExprFloatLiteral:

``ExprFloatLiteral``
~~~~~~~~~~~~~~~~~~~~

Base: :ref:`Expr <lint-node-Expr>`.

Represents a floating-point literal value.

PSS 3.1 §4.6 admits two spellings, both modelled here: a plain decimal form (``1.5``) and a scientific form (``1.5e-3``). They differ only in notation, not in value, so ``is_scientific`` exists to let a consumer reproduce the source spelling rather than to change how the value is interpreted.

Both the parsed value and the source text are kept. ``value`` is what a consumer evaluates; ``image`` is what it needs to reproduce the source, and the two are not interchangeable. Digit separators and trailing zeros do not survive a round trip through a double, and not every decimal fraction is exactly representable, so ``image`` is the authority on spelling and ``value`` on magnitude.

.. code-block:: none

   float32 a = 1.5;
   float64 b = 1.0e-9;
   float64 c = 1_000.5;

     - Description
   * - ``value``

   * - ``image``
     - ``string``
     - Original text representation from source, separators included
   * - ``is_scientific``
     - ``bool``
     - True when written in exponent notation

.. _lint-node-ExprSliceRange:

``ExprSliceRange``
~~~~~~~~~~~~~~~~~~

Base: :ref:`Expr <lint-node-Expr>`.

A ``[ lower .. upper ]`` range used to select a sub-range of a collection or a string.

Annex B defines two rules with \*identical\* syntax:

\* ``array_slice  ::= expression .. expression | expression .. | .. expression`` \* ``string_slice ::= expression .. expression | expression .. | .. expression``

Which one a given range is cannot be decided while parsing -- it depends on the type of the operand being sliced, which is only known after name resolution. A single neutral node is therefore the only shape the builder can honestly produce; the linker classifies it. (Contrast ``ExprBitSlice``, which is spelled ``[msb : lsb]`` and \*is\* syntactically distinct.)

Either endpoint may be absent, but not both -- ``[..]`` is not a legal slice. An absent endpoint means "to the end of the collection" in that direction.

The node appears as an element of ``ExprMemberPathElem.subscript``. A subscript that is a slice yields the \*collection\* type, whereas a plain index subscript yields the \*element\* type -- consumers that walk subscripts must distinguish the two.

.. code-block:: none

   unique arr[2..5];       // array slice: elements 2 through 5
   string tail = s[3..];   // string slice: from index 3 onward
   string head = s[..3];   // string slice: up to index 3

   :header-rows: 1
   :widths: 20 25 55

   * - Field
     - Type
     - Description
   * - ``lower``
     - :ref:`Expr <lint-node-Expr>`
     - Left index, or null when written as ``[..upper]``
   * - ``upper``
     - :ref:`Expr <lint-node-Expr>`
     - Right index, or null when written as ``[lower..]``

.. _lint-node-ConstraintStmtSoft:

``ConstraintStmtSoft``
~~~~~~~~~~~~~~~~~~~~~~

Base: :ref:`ConstraintStmt <lint-node-ConstraintStmt>`.

Soft (overridable) constraint statement -- PSS 3.1, §13.1.12.

A soft constraint expresses a \*preference\* rather than a requirement. It is discarded when it contradicts a hard constraint, an active default constraint, or a higher-priority soft constraint, instead of producing a solve failure.

Relative priority is determined by \*position in the model\*, not by anything written in the source: a soft constraint declared later outranks one declared earlier in the same scope, a derived type outranks its base, and a type extension outranks the initial declaration. The parser's obligation is therefore to preserve declaration order faithfully -- ``ConstraintStmt::index`` records the position within the enclosing scope, and priority is derived from it downstream. Reordering constraint-scope children would silently change what the model means.

.. code-block:: none

   action A {
       rand int x;

       constraint c {
           x < 100;            // hard -- always holds
           soft x > 10;        // preference, lower priority
           soft x in [50..60]; // preference, higher priority
       }
   }

   :header-rows: 1

     - Description

.. _lint-node-ConstraintStmtUnique:

``ConstraintStmtUnique``
~~~~~~~~~~~~~~~~~~~~~~~~

Base: :ref:`ConstraintStmt <lint-node-ConstraintStmt>`.

Uniqueness constraint ensuring distinct values.

Constrains a set of expressions to have mutually distinct values during randomization. All expressions in the list must evaluate to different values, preventing duplicates within the specified set.

.. code-block:: none

   action transaction_set {
       rand bit[8] id1, id2, id3, id4;
       rand bit[16] addr[4];

       constraint unique_ids_c {
           unique { id1, id2, id3, id4 };
       }

       constraint unique_addresses_c {
           unique { addr[0], addr[1], addr[2], addr[3] };
       }

       constraint mixed_unique_c {
           unique { id1, id2, id3 };  // First three must differ
           // id4 is not constrained by this
       }
   }

PSS 3.1 (§13.1.10) admits a second, single-argument form whose meaning is \*different\*:

.. code-block:: none

   unique { a, b, c };   // these three attributes must differ
   unique arr;           // the elements of `arr` must differ
   unique arr[2..5];     // elements 2..5 of `arr` must differ

Both forms populate ``list``, so ``is_braced`` is what distinguishes them: with one entry, ``unique { a }`` constrains a single scalar (vacuously true) while ``unique a`` constrains every element of a collection. A consumer that ignores the flag will silently mis-interpret one of them.

A slice on the single-argument form is not carried here -- it is part of the ``hierarchical_id``, as the trailing subscript of its last ``ExprMemberPathElem`` (an ``ExprSliceRange``).

ActivityMatch provides multi-way branching based on pattern matching against an expression value. It's similar to a switch statement, allowing matching against specific values, ranges, or a default case.

.. code-block:: none

   action my_action {
       rand bit[8] opcode;

       activity {
           match (opcode) {
               // Single value
               [0x00]: { do comp.nop_action; }

               // Multiple values
               [0x01, 0x02, 0x03]: { do comp.arithmetic; }

               // Range
               [0x10..0x1F]: { do comp.memory_ops; }

               // Multiple ranges
               [0x20..0x2F, 0x40..0x4F]: { do comp.control; }

               // Default case
               default: { do comp.illegal_opcode; }
           }
       }
   }

.. _lint-node-ActivityParallel:

``ActivityParallel``
~~~~~~~~~~~~~~~~~~~~

Base: :ref:`ActivityLabeledScope <lint-node-ActivityLabeledScope>`.

Defines a parallel execution block with join semantics.

ActivityParallel specifies that its contained activities may execute concurrently. The join specification determines when the parallel block completes relative to its branches. By default, all branches must complete.

.. code-block:: none

   action my_action {
       activity {
           // Default parallel (wait for all)
           parallel {
               do comp.action1;
               do comp.action2;
               do comp.action3;

           // Parallel with join_first
           parallel join_first(2) {
               do comp.fast_action;
               do comp.medium_action;
               do comp.slow_action;
           }

           // Parallel with join_none (fire and forget)
           parallel join_none {
               do comp.background1;
               do comp.background2;
           }
       }
   }

``ActivitySchedule``

ActivitySchedule allows activities to execute with explicit scheduling constraints that define relative ordering. Unlike parallel blocks where all actions start together, schedule blocks allow fine-grained control over when each activity begins and ends relative to others.

               a before b;           // Sequential
               a before c;           // Sequential
               parallel(b, c);       // Parallel
               b before d;
               c before d;
           }

.. _lint-node-ActivitySelect:

``ActivitySelect``
~~~~~~~~~~~~~~~~~~

Base: :ref:`ActivityLabeledScope <lint-node-ActivityLabeledScope>`.

Randomly selects and executes one branch from alternatives.

ActivitySelect provides a weighted random choice between multiple branches. Each branch can have a guard condition and a weight expression to control selection probability. Only one branch is executed per select statement.

.. code-block:: none

   action my_action {
       rand bit[8] mode;

       activity {
           // Basic select (equal probability)
           select {
               1: { do comp.option_a; }
               1: { do comp.option_b; }
               1: { do comp.option_c; }
           }

           // Weighted select
           select {
               70: { do comp.common_case; }
               20: { do comp.rare_case; }
               10: { do comp.very_rare_case; }
           }

           // Select with guards
           select {
               [mode == 0] 1: { do comp.mode0_action; }
               [mode == 1] 1: { do comp.mode1_action; }
               [mode == 2] 1: { do comp.mode2_action; }
           }
       }
   }

   :header-rows: 1
   :widths: 20 25 55

   * - Field
     - Type
     - Description
   * - ``branches``
     - list of :ref:`ActivitySelectBranch <lint-node-ActivitySelectBranch>`

.. _lint-node-ActivitySelectBranch:

``ActivitySelectBranch``
~~~~~~~~~~~~~~~~~~~~~~~~

Represents one branch in an activity select statement.

ActivitySelectBranch encapsulates a single alternative in a select statement, including its optional guard condition, weight expression, and body. The guard determines if the branch is eligible for selection, and the weight influences the selection probability among eligible branches.

.. code-block:: none

   action my_action {
       rand bit[8] value;

       activity {
           select {
               // Branch with guard and weight
               [value < 50] 70: {
                   do comp.low_value_action;
               }

               // Branch with only weight
               20: {
                   do comp.medium_value_action;
               }

               // Branch with guard only (implicit weight 1)
               [value > 200]: {
                   do comp.high_value_action;
               }
           }
       }
   }

     - Optional condition that must be true for branch to be eligible

.. _lint-node-ActivitySequence:

``ActivitySequence``
~~~~~~~~~~~~~~~~~~~~

Base: :ref:`ActivityLabeledScope <lint-node-ActivityLabeledScope>`.

Defines a sequential execution block.

ActivitySequence specifies that its contained activities execute in strict sequential order, one after another. Each activity completes before the next begins. This is the default execution model and can be explicitly specified with the 'sequence' keyword.

.. code-block:: none

   action my_action {
       activity {
           // Explicit sequence
           sequence {
               do comp.init_action;
               do comp.process_action;
               do comp.cleanup_action;
           }

           // Labeled sequence
           setup_phase: sequence {
               do comp.config;
               do comp.verify;
           }

           // Nested sequences
           sequence {
               sequence {
                   do comp.step1;
                   do comp.step2;
               }
               do comp.step3;
           }
       }
   }

.. _lint-node-ActivitySuper:

``ActivitySuper``
~~~~~~~~~~~~~~~~~

Base: :ref:`ActivityLabeledStmt <lint-node-ActivityLabeledStmt>`.

Invokes the super-class activity implementation.

ActivitySuper allows a derived action to call the activity block defined in its parent action class. This enables activity inheritance and extension similar to method overriding in object-oriented programming.

.. code-block:: none

   action base_action {
       activity {
           do comp.init;
           do comp.process;
       }
   }

   action derived_action : base_action {
       activity {
           do comp.setup;
           super;              // Execute base_action's activity
           do comp.cleanup;
       }
   }

   action extended_action : base_action {
       activity {
           super;              // Just execute parent activity
       }
   }

.. _lint-node-SymbolDeclaration:

``SymbolDeclaration``
~~~~~~~~~~~~~~~~~~~~~

Base: :ref:`SymbolScope <lint-node-SymbolScope>`.

A named, reusable activity fragment -- LRM B.9, ``symbol_declaration``.

``symbol s(int n) { do A; do B; }`` declares a fragment that a ``symbol_call`` inlines at its call site. It is a scope so its parameters and the labels of its body statements resolve, and so a call can name it.

.. _lint-node-ExecBlockTag:

``ExecBlockTag``
~~~~~~~~~~~~~~~~

Base: :ref:`ScopeChild <lint-node-ScopeChild>`.

Tag on a target-template exec block -- PSS 3.1 §20.5.4.

``exec_block_tag ::= type_identifier [ struct_literal ]``

A tag exists solely so a code generator can tell whether two exec blocks are equivalent and may be coalesced. It has no effect on action traversal, solving, or runtime execution.

It is evaluated using a temporary instance of the named struct type, initialized from the struct literal when one is written and from the field defaults otherwise. Two blocks match only if their tags are the same struct type \*and\* evaluate equal; an untagged block matches nothing, not even another untagged block.

Tags are permitted only on ``header``, ``declaration``, ``run_start``, ``run_end`` and ``exec file`` blocks -- not on native exec blocks, not on ``body``, and not on the solve execs. That restriction is a semantic rule, not a grammatical one, and is reported as PSS106.

.. code-block:: none

   exec header C = tag_s {.name = "hdr"}: """
       #include <stdio.h>
   """;

.. _lint-node-ProceduralStmtSuper:

``ProceduralStmtSuper``
~~~~~~~~~~~~~~~~~~~~~~~

Base: :ref:`ExecStmt <lint-node-ExecStmt>`.

Invokes the base type's implementation of the enclosing exec block.

ProceduralStmtSuper represents the ``super;`` statement inside an exec block. Without it, a derived type's exec silently \*replaces\* the base's rather than extending it, so this is the correct form of the most damaging inheritance mistake in PSS.

The statement carries no operands: which exec block it refers to is fixed by where it appears -- the same kind, on the base type.

.. code-block:: none

   action base_a {
       exec body {
           console.log("base");
       }
   }

   action derived_a : base_a {
       exec body {
           super;                  // run base_a's exec body first
           console.log("derived");
       }
   }

.. _lint-node-TargetTemplateFunction:

``TargetTemplateFunction``
~~~~~~~~~~~~~~~~~~~~~~~~~~

Base: :ref:`ScopeChild <lint-node-ScopeChild>`.

Function whose body is target-language template text -- PSS 3.1 §20.6.

A target-template function declares a PSS prototype but supplies its implementation as a string of target-language code rather than as a PSS body.  The string is a template: inside a triple-quoted string it may contain mustache expressions and control-flow directives, and those resolve against the function's own parameter list.

       target C function void store(int a) = """ stw {{a}}, 0 """;

       // Static form
       target C static function int read() = """ return *p; """;

.. _lint-node-MonitorActivityConcat:

``MonitorActivityConcat``
~~~~~~~~~~~~~~~~~~~~~~~~~

Base: :ref:`MonitorActivityLabeledScope <lint-node-MonitorActivityLabeledScope>`.

.. code-block:: none

   component c {
       action phase1 { }
       action phase2 { }

       monitor protocol_monitor {
           phase1 p1;
           phase2 p2;

           activity {
               concat {
                   p1;
                   p2;
               }
           }
       }
   }

``MonitorActivityStmt``
~~~~~~~~~~~~~~~~~~~~~~~

Base: :ref:`ScopeChild <lint-node-ScopeChild>`. Subclasses: :ref:`MonitorActivityLabeledStmt <lint-node-MonitorActivityLabeledStmt>`, :ref:`MonitorConstraint <lint-node-MonitorConstraint>`.

Base class for all monitor activity statements.

MonitorActivityStmt is the abstract base class for the non-scope statements that can appear within a monitor's activity block. The block-shaped forms (``sequence``, ``concat``, ``overlap``, ``schedule``, ``select``) descend from MonitorActivityLabeledScope instead, because they introduce a scope; the two branches meet at ScopeChild. Any field holding an arbitrary monitor activity statement must therefore be typed ``ScopeChild``, not ``MonitorActivityStmt`` -- typing it narrowly silently discards every block-shaped body.

.. code-block:: none

   monitor protocol_monitor {
       action_t req, ack, grant;
       activity {
           req;                          // action traversal
           eventually grant;             // MonitorActivityEventually
           constraint { req.len > 0; }   // MonitorConstraint
       }
   }

A ``constraint`` statement inside a monitor's activity block.

This covers ``monitor_activity_constraint_stmt`` only -- a ``constraint`` appearing among the \*statements\* of a monitor activity, where its position in the statement order is meaningful. A ``constraint`` in the monitor \*body\* is a ``monitor_constraint_declaration`` and builds an ordinary ConstraintBlock, exactly as it does in an action or struct, so the linker and every constraint consumer treat it uniformly.

A monitor activity constraint is not labelable, which is why this descends from MonitorActivityStmt rather than MonitorActivityLabeledStmt.

.. code-block:: none

   component c {
       action req { rand bit[8] priority; }

       monitor protocol_monitor {
           req r;

           constraint c1 { r.priority > 0; }

           activity {
               constraint { r.priority inside [1..8]; }
               r;
           }
       }
   }

.. _lint-node-OverrideDecl:

``OverrideDecl``
~~~~~~~~~~~~~~~~

Base: :ref:`Scope <lint-node-Scope>`.

An ``override { ... }`` block.

Overrides retarget type selection during elaboration: every place the model would have used the target type or instance, it uses the replacement instead. The block's statements are held in ``getChildren()`` and are in source order, which matters -- a later statement overriding the same target wins.

The block declares no names, so it introduces no scope in the linked tree even though it is a ``Scope`` in the AST.

.. code-block:: none

   component pss_top {
       action A { }
       action B : A { }

       sub s1, s2;

       override {
           type A with B;
           instance s1.a with B;
       }
   }
