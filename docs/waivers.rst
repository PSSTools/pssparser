################
Waiving findings
################

A waiver says "this finding, here, is intended", in the PSS source next to the
code it excuses.  It is the narrow alternative to turning a rule off for the
whole project with ``[severity] ID = "off"``.  Every waiver gives a reason,
and pssparser reports a waiver that no longer matches anything, so waivers do
not pile up after the code they excused has been fixed.

There are two forms: an annotation, which follows the model's structure, and
a comment, which works anywhere, including in vendored or generated code.

The annotation
==============

.. code-block:: pss

   package regs {
       struct ctrl_s {
           @lint_pkg::waive {.id = "enum-item-hides-declaration",
                             .reason = "BURST is the field's legacy name"}
           mode_e mode;
       }
   }

``@lint_pkg::waive`` is declared by pssparser in the built-in ``lint_pkg``
package, which needs no import.  Write it fully qualified, as above:
pssparser recognises the waiver by that name.

``.id``
   The rule to waive: a marker ID (``LINT401``), a rule name
   (``enum-item-hides-declaration``), or any rule selector from
   :doc:`lint` -- ``family:constraint``, a tier such as ``style``, an ID
   prefix such as ``LINT4``.  To waive several unrelated rules, stack
   several annotations, or separate the IDs with commas.

``.reason``
   Why the finding is intended.  A waiver without one still applies, but is
   reported (``PSSP205``).

What it covers depends on the form of the annotation (LRM 7.13):

Element annotation (no ``;``)
   The element that follows, from the annotation to the element's end: a
   declaration and everything in it, one activity or procedural statement,
   one constraint item, one ``import``.

Standalone annotation (ends with ``;``)
   From the annotation to the end of the enclosing scope.  At file scope,
   the rest of the file.

   .. code-block:: pss

      package generated {
          @lint_pkg::waive {.id = "style", .reason = "generated by regtool"};
          // ... every style finding from here to the end of the package
      }

A diagnostic is covered when its **primary** location -- the one in its
``file:line:col`` -- is in the span.  A related ``note:`` location does not
count, so waiving a declaration does not silence every warning that points
back at it.

Another PSS tool disregards an annotation it does not recognise (LRM 7.13),
so a model with waivers is still portable.  For a tool that wants the
package declared, copy the declaration from ``lint_pkg.pss`` in pssparser's
standard library (``pssparser.get_stdlib_dir()``):

.. code-block:: pss

   package lint_pkg {
       annotation waive {
           string id;
           string reason;
       }
   }

The comment
===========

.. code-block:: pss

   import vendor::*;   // pssparser waive LINT402: vendor header order
   // pssparser waive LINT601, LINT602: pre-3.1 model, migrating in Q1
   short_xfer;

``// pssparser waive <id>[, <id>...]: <reason>``.  A comment that follows
code on a line covers that line.  A comment alone on its line covers the
next line that holds code.  Only ``//`` comments count; the same text in a
``/* */`` comment or a string is not a waiver.

Use the comment where the annotation cannot go: inside an expression, in a
template string, or in a file you would rather not restructure.

What cannot be waived
=====================

An error that means the model was not built -- an LRM violation, or a
failure of pssparser itself -- is never waived.  Waiving it would report
success for a run that compiled nothing.  A waiver that names one has no
effect and is reported (``PSSP204``).

The waiver markers below cannot be waived in the source either; a waiver
could otherwise hide the warning that it is itself unused.  ``[severity]``
can re-level them like any other marker.

Order of evaluation
===================

.. code-block:: text

   lint selection  ->  [severity]  ->  waivers  ->  -Werror / --no-warnings  ->  output

* After ``[severity]``: a waiver covers a rule the project promoted to an
  error.  The most specific statement wins.
* Before ``-Werror``: a waived warning is never promoted.

When a run fails to parse, there is no model to read annotations from, and
only comment waivers apply.  Such a run fails anyway.  When it parses but
fails to link, both forms apply.

Waiver markers
==============

``PSSP202`` -- unused waiver
   The waiver matched no diagnostic, although a rule it names ran.  Delete
   it if the finding was fixed.  A waiver for a rule that did not run --
   turned ``off``, outside the lint profile, or from a checker that was not
   loaded -- is not reported, so waivers do not come and go with the
   configuration.
``PSSP203`` -- unknown rule
   The ``id`` names nothing a loaded checker declares.  The message
   suggests the nearest match.  A rule from an extension that is not
   installed looks the same.
``PSSP204`` -- waiver on an error
   See *What cannot be waived*.
``PSSP205`` -- no reason
   ``.reason`` is missing or empty, or the comment has no ``: text``.

A waiver that names an old ID -- a retired one (``PSS053``), or a rule's
former ID (its ``aliases``) -- still works and gets a ``PSSP004`` note
naming the current one.

Seeing what was waived
======================

* The summary line counts them: ``0 errors in 3 files (2 waived)``.
* ``--show-waived`` prints them too, each marked ``[waived: <reason>]``.
  The exit code is unchanged.
* ``--format json`` lists them in a top-level ``waived`` array, each with
  a ``waiver`` object.  They are not in ``diagnostics`` or in the
  ``summary`` counts.  See :doc:`diagnostics-json`.
* ``--format sarif`` reports them as results with an ``inSource``
  suppression whose justification is the reason, so a code-scanning UI
  shows them as dismissed.
* ``--stats`` adds a ``waived:`` row with a count per ID.

To see everything, for a strict CI job, turn source waivers off:

.. code-block:: toml

   [waivers]
   source = false

From Python
===========

The CLI's matching is a library function, so another tool applies the same
waivers:

.. code-block:: python

   from pssparser import Parser, waivers

   p = Parser()
   p.parse(files)
   p.link()
   found = waivers.collect(p, files)
   result = waivers.apply(p.markers, found, rules=rule_set,
                          is_core_error=is_core_error, ran=None)
   # result.kept, result.waived, result.markers

``rules`` is a ``pssparser.checkers.selectors.RuleSet`` over the marker
catalogue, and ``ran`` is the set of codes whose rule ran (``None`` turns
the unused-waiver check off).  Markers need a ``code``; the CLI assigns
codes to the linker's markers before it applies waivers.

The CLI collects and applies waivers in the core lint engine, which the
WebAssembly build shares, so an editor applies the same ones.  With an
engine that knows the marker catalogue
(``pssparser.lint.selection.tell_engine``), ``waivers.collect_in(engine, p,
files)`` and ``waivers.apply_in(engine, p.markers, found, ran=None)`` do the
same as the two calls above.  From TypeScript (``@psstools/pssparser``):

.. code-block:: typescript

   parser.setHostMarkers(catalogue);       // the markers the CLI knows
   parser.parseSources(sources);
   parser.link();
   const found = parser.collectWaivers(sources);
   const result = parser.applyWaivers(found, parser.markers, ran);
   // result.kept and result.waived index the diagnostics given
