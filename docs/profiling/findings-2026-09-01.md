# Grammar profiling — first findings

**Run.** `scripts/profile_grammar.py --mode both`, grammar `11937d553c14`, corpus `efa1ef2`
(85 files in the `parses = true` buckets, 5,299 lines, 25,671 tokens). Harness and methodology:
[`../design/grammar-profiling-harness.md`](../design/grammar-profiling-harness.md).

> **Outcome (same day).** F4 was acted on: `function_decl` and `procedural_function` were merged
> into one left-factored rule. Corpus parse time **46.3 ms → 26.4 ms, 1.75× faster**; total SLL
> lookahead −9.1%. Grammar is now `e0144fe836f9` and the baseline has been regenerated. Details in
> §4. Everything below §4 describes the grammar *before* that change and is left as the record of
> what the first run found.
>
> Note what did **not** change: LL fallbacks are still 548 and ambiguities still 266. F4 was a
> lookahead-cost hotspot, not a fallback one. The fallback conclusions in §1 stand.

---

## 0. The methodology held

Cold and warm runs report **identical** lookahead counters — 27,967 SLL, 15,062 predictions, 548
LL fallbacks, 266 ambiguities — while ATN transitions differ by 3.7× (4,698 cold, 1,265 warm).

That is the design's central claim confirmed on real data: `SLL_TotalLook` is independent of DFA
warmth and can be ranked and gated on, `*_ATNTransitions` measures the process rather than the
grammar and cannot. The baseline gate is built on the first and reports the second.

Prediction is **68% of parse wall time** under profiling. That is an upper bound — profiling adds a
clock read per prediction and disables fast paths — but it is high enough that the "is this worth
caring about?" question is answered yes, which was not a foregone conclusion.

## 1. Ambiguities — correctness, not cost

Eleven decisions are ambiguous over this corpus. Ambiguity is not a performance signal: ANTLR
resolves one by silently taking the lowest-numbered alternative, so each entry is a place where the
grammar describes two parses and the parser picks one without reporting anything.

### F1 — `template_param_value` is ambiguous by construction (172 occurrences, 172 LL fallbacks)

```antlr
template_param_value:
    data_type
    | constant_expression // Note: both expression and data_type cover 'identifier'
    ;
```

The grammar's own comment states the ambiguity. It fires on **172 of 240 invocations** — 72% — and
is by some distance the worst ratio in the grammar. Every one also costs an LL fallback, making
this rule 172 of the corpus's 548 fallbacks on its own.

**It is not a parse bug.** ANTLR always takes `data_type`, and `TaskBuildParamValList` reclassifies
downstream ("Value parameter used as a type parameter"). Both enum-valued and type-valued arguments
link correctly, and distinct value arguments produce distinct specializations.

**What does leak** is the diagnostic. An undefined name in a *value* parameter position is reported
as a type error:

```pss
struct S <int M = 1> { int x; }
component c { S<no_such_thing> a; }
```
```
Error: unknown type 'no_such_thing' t.pss:4:20
```

The name was never in a type position; the user is told about a type they did not write. Filed as
**PF-A1** in [`../design/known-issues.md`](../design/known-issues.md).

This one is *not* fixable by left-factoring, and should not be attempted: a type reference and a
constant reference are genuinely spelled alike in PSS, so the grammar cannot distinguish them and
the reclassification has to happen after name resolution. The actionable part is the diagnostic.

### F2 — `expression`, 40 ambiguities and 280 LL fallbacks

Decision 302 is the precedence loop ANTLR generates from the left-recursive `expression` rule
(fourteen binary-operator alternatives, `PSSParser.g4:1780`). Its evidence spans are all
precedence-climbing boundaries:

```
ambiguity   25:33   * DMA_CH_STRIDE;
ambiguity   100:55  * DMA_CH_STRIDE +
ambiguity   67:66   == 0
ambiguity   35:27   <= 4096;
```

`expression` is the top rule by lookahead share (11.1%) and owns 280 of 548 LL fallbacks. Together
with F1 that is **452 of 548 — 82% of all LL fallbacks come from two rules.**

Unlike F1 this is a cost signal, and the cause is structural rather than a defect: encoding fourteen
precedence levels as alternatives of one left-recursive rule is what the comment at
`PSSParser.g4:1776` describes as a deliberate divergence from the LRM. Whether the ambiguities
change any parse needs a separate check before anything is touched — they may all be resolved
identically by precedence. **Do not restructure `expression` on the strength of this number alone.**

### F3 — `monitor_field_declaration` / `monitor_activity_stmt` (17 + 22 occurrences)

```
monitor_field_declaration:
    const_field_declaration | action_handle_declaration | monitor_handle_declaration
```

Evidence: `dut_c::write w;` at `43:8`, and the bare `w;` traversal at `48:16`. An action handle and
a monitor handle declaration are spelled identically — `type_identifier identifier ;` — so nothing
in the token stream distinguishes them and ANTLR takes `action_handle_declaration` every time.

This is the ambiguity most likely to be a *real* misparse. Unlike F1, no reclassification pass was
found: there is no `visitMonitor_handle_declaration` override in `AstBuilderInt` at all, so the
alternative ANTLR discards has no visitor to restore it. Whether that loses anything depends on
whether a monitor handle needs an AST node distinct from an action handle, which was **not
established** — the parse is silently resolved either way, which is exactly what makes it worth
checking. Filed as **PF-A2**.

### F4 — `component_body_item`: the clearest left-factoring candidate

look/inv **7.6** over 36 tokens of maximum lookahead, with no ambiguity and no LL fallback — the
signature of a decision that is correct but has to read a long way to commit. The evidence is
unambiguous about why:

```
sll-max-look  23:4  36 tokens  target function void check(addr_handle_t base, bit[32] nbytes, mem_...
sll-max-look  31:4  19 tokens  target function void configure_channel(int ch, dma_xfer_s xfer) {
sll-max-look  48:4  31 tokens  solve function void initialize(addr_handle_t base, bit[64] tx_addr, ...
sll-max-look  13:4   1 tokens  action
```

`action` decides in one token. The function-declaration family — plain, `target`, `solve`,
`import`, `extern`, each with a full parameter list — shares a prefix long enough that the parser
reads the entire signature before it can pick an alternative. Left-factoring the function forms into
a single alternative with the qualifier hoisted is the standard remedy and this is a textbook
instance of it.

`function_parameter_list_prototype` at look/inv 8.1 (rank 11) is the same construct seen from
inside, and would likely improve with it.

### F5 — high invocation, low cost: leave alone

`member_path_elem` (1,919 invocations, look/inv 1.0) and `primary` (1,751, look/inv 1.0) are ranked
3rd and 7th by total lookahead purely because they are hot. Each decides in one token. There is
nothing to fix, and the `look/inv` column exists precisely so these do not read as hotspots.

## 3. The fallbacks, specifically

548 LL fallbacks, and the two rules holding 82% of them are both **unfixable by grammar work**. This
was checked rather than assumed.

**`expression` — 280 (51%), inherent.** Decision 302 is not written in the grammar; it is the
precedence-climbing loop ANTLR generates from the left-recursive rule, and the generated code guards
its thirteen operator alternatives with **13 `precpred(_ctx, N)` calls**. Those predicates read the
parser's precedence context, which SLL prediction does not have — so escalation to LL is structural.
Any left-recursive rule with fourteen precedence levels behaves this way. Nothing to do.

**`template_param_value` — 172 (31%), not left-factorable.** The obvious fix is to drop the
`data_type` alternative and let `constant_expression` cover the shared identifier surface, since the
grammar's own comment says both cover `identifier`. **This does not work:** `member_path_elem`
(`PSSParser.g4:1985`) is `identifier function_parameter_list? member_path_elem_index*` — it has no
`template_param_value_list`, so `expression` cannot parse `S<int>`; it would read `S < int` as a
comparison. Removing the `data_type` path would break every nested template type argument. The
ambiguity stays; see PF-A1 for the part that is worth fixing (the diagnostic).

**The remaining 96** are spread over 13 decisions, none above 39.

So the only lever that reaches the fallbacks at all is **two-stage parsing** — SLL with
`BailErrorStrategy` first, re-parsing with LL on failure. Measured on this corpus by temporarily
forcing `PredictionMode::SLL` (patch reverted):

| | corpus parse, unprofiled |
| --- | ---: |
| LL (as shipped) | 45.6 ms |
| SLL only | 22.1 ms — but 3 of 84 files get spurious syntax errors |
| **two-stage (SLL, LL re-parse on failure)** | **24.4 ms — 1.87×** |

Only 3 files need stage 2 (`std_pkg.pss`, `extension_variants.pss`,
`procedural_realization.pss`), and they are re-parsed with LL, so results are identical. Not
implemented — it changes error handling rather than the grammar, and was deferred in favour of F4.

Worth noting *why* `std_pkg.pss` failed under SLL: at `function void print(string fmt);` — the same
construct as F4. The two findings were one defect seen from two directions.

## 4. What was done — F4, left-factoring the function forms

`function_decl` (`... ;`) and `procedural_function` (`... { ... }`) were identical up to the end of
`function_prototype` and were offered as **separate alternatives** of both `package_body_item` and
`component_body_item`. Merged into one rule with a trailing one-token choice:

```antlr
function_decl:
	platform_qualifier? is_pure=TOK_PURE? TOK_STATIC? TOK_FUNCTION function_prototype
	( TOK_SEMICOLON | TOK_LCBRACE procedural_stmt* TOK_RCBRACE )
	;
```

The two AST-builder visitors became one that branches on `ctx->TOK_SEMICOLON()`. The AST is
unchanged — a declaration still builds a bare `IFunctionPrototype`, a definition still wraps one in
an `IFunctionDefinition`.

| | before | after |
| --- | ---: | ---: |
| corpus parse (unprofiled, best of 5) | 46.3 ms | **26.4 ms** (1.75×) |
| total SLL lookahead | 27,967 | **25,425** (−9.1%) |
| `component_body_item` decision | 2,903 look, 7.6 look/inv, 36 maxLA | gone from the top 25 |
| `package_body_item` decision | 1,560 look, 2.8 look/inv, 25 maxLA | gone from the top 25 |
| LL fallbacks / ambiguities | 548 / 266 | 548 / 266 (unchanged, as expected) |

Full suite 3296 passed, 0 failed, same 12 xfails — the merge is behaviour-preserving.

The wall-clock gain (1.75×) is much larger than the lookahead reduction (9.1%) because ATN
simulation cost is superlinear in lookahead depth: one decision reading 36 tokens 384 times is worth
far more than its token count suggests. This is the case for keeping `look/inv` and `maxLA` in the
report next to the totals — ranking on totals alone would have put this decision second and made it
look like a 10% opportunity rather than a 43% one.

`static` is still dropped on both spellings — `mkFunctionPrototype` never recorded it and neither
visitor set it. Pre-existing, unchanged here, and out of scope for a performance refactor.

## 5. What to do next

Ordered by confidence, not by size of number:

1. ~~**F4 (`component_body_item`)** — left-factor the function-declaration forms.~~ ✅ done, §4.
2. **PF-A2 (`monitor_field_declaration`)** — establish whether the misparse is real. Two
   alternatives, different AST nodes, no reclassification pass found. Smallest scope, highest chance
   of being a genuine bug.
3. **Two-stage parsing** — measured at 1.87× in §3 and the only remaining lever on the 548
   fallbacks. Independent of the grammar; the risk is in error handling and diagnostics. Re-measure
   after F4, since F4 removed the construct that made `std_pkg.pss` fail under SLL and the two-stage
   win may now be larger or the fallback set smaller.
4. **PF-A1 (`template_param_value`)** — fix the diagnostic, not the grammar.
5. **F2 (`expression`)** — investigate only, and only for correctness. The 280 fallbacks are
   structural (§3) and will not move. The open question is whether the 40 ambiguities change any
   parse; the precedence encoding is deliberate.

Two follow-on experiments the harness now makes measurable rather than speculative:

- **Two-stage parsing** (SLL + `BailErrorStrategy`, LL on failure). Its payoff is bounded by the LL
  fallback volume, which is 548 — 82% of it from two rules. Fixing those first may make the whole
  optimization unnecessary, which is worth knowing before writing it.
- **DFA persistence across processes.** Cold costs 4,698 ATN transitions against warm's 1,265 —
  3,433 transitions is the entire one-time cost of learning this corpus. Note that cold and warm
  *wall* times came out within noise of each other (1.07 s vs 1.13 s) on a corpus this small, so
  the transition count is the honest measure and the time difference is not yet resolvable. If the
  idea is pursued, amplify with `--repeat` first to get a time that means something.
